O problema

Mídia em ônibus é vendida no escuro

Outdoor tem fluxo de carros medido. TV tem IBOPE. Digital tem clique. Mas o anúncio no ônibus que cruza a cidade inteira é vendido sem nenhum número de audiência — só intuição. O uAI OOH preenche exatamente essa lacuna.

🕳️

Zero métrica

Não há audiência publicada para mídia em ônibus de BH. O preço hoje é negociado por "feeling" — sem base comparável entre linhas.

🗺️

Os dados existem — espalhados

A PBH publica itinerários, bilhetagem, pontos, censo, malha viária. Mas em 27 arquivos crus, com 3 sistemas de coordenadas e IDs que não se conversam.

🎯

A oportunidade

Quem cruzar esses dados primeiro tem um ativo proprietário: o ranking de audiência das linhas — e a base para precificar mídia OOH em BH com método.

O produto

Dois formatos, duas formas de medir

A mídia em ônibus tem duas naturezas — e cada uma exige uma medição diferente. Confundir as duas é o erro que o produto evita por construção.

Mídia interna

🪑 Backseat — anúncio nos assentos

Quem vê é quem está a bordo. A audiência é medida diretamente pelos passageiros transportados — não é proxy.

  • Fonte principal: MCO (Mapa de Controle Operacional) — passageiros por veículo/viagem/dia
  • Instalado em carros específicos → soma-se os carros reais da campanha (a frota é desigual)
  • Perfil por faixa horária vem do embarque por ponto (distribuição, não volume)
  • Vende-se por linha inteira ou por carros específicos
Mídia externa

🚌 Back bus — anúncio na traseira

Quem vê é quem o ônibus passa na rua: pedestres, motoristas, gente nos pontos. A audiência é estimada por exposição.

  • Pessoas nos pontos do trajeto (embarque, modulado por velocidade de passagem)
  • Moradores na frontagem (~30m do trajeto, via censo)
  • Exposição arterial: quanto do trajeto roda em via de alto fluxo
  • Trânsito/congestionamento como dwell time → v2 (coletor próprio)
⚖️
Impressões ≠ alcance. O produto mede impressões (OTS — contatos visuais): uma mesma pessoa conta várias vezes no mês. Alcance (pessoas únicas) só seria mensurável deduplicando pela matriz Origem-Destino da bilhetagem. Vender "impressões" é defensável hoje; "alcance único" exige outra camada.

Como os cálculos são realizados

Do traçado cru à impressão estimada

O trabalho pesado é geográfico: o PostGIS cruza o corredor de cada linha com as camadas de contexto e materializa tabelas planas. O app Java de produção só faz SELECT — nada de geometria em tempo de consulta.

1

Corredor da linha

Para cada linha, ST_Buffer(shape, 300m) desenha o corredor. O traçado é por tipo de dia — a mesma linha desvia no domingo (ex.: a 4107 contorna a Feira Hippie).

2

Cruzamento com o censo → população & renda

Interseção corredor ∩ setores censitários, ponderada por área (não superestima): pop_pond = Σ pop × área_intersecção / área_setor. Daí saem população do corredor, renda média ponderada e a distribuição de classes A–E.

3

POIs e exposição arterial

POIs dentro do corredor por categoria. E pct_arterial = quanto do traçado roda sobre via de alto fluxo — onde a linha passa, não volume de carros.

4

Demanda

MCO agregado por linha/tipo de dia → passageiros/dia. Embarque normalizado → curva horária (distribuição).

5

Impressões & score

Combina tudo nas fórmulas abaixo e normaliza entre as 304 linhas para o score 0–100.

📐 Modelo de impressões — back bus (por tipo de dia)

E_pop(d) = pop_corredor_pond × f_exposicao(0,15) × freq_norm(d)
E_pax(d) = passageiros_dia(d) × p_vista_traseira(0,6)
E_traf(d) = 0 # volume/congestionamento → v2
Impressões(d) = E_pop + E_pax + E_traf
Impressões/mês = Σ Impressões(d) × dias(d)
🎚️
Os coeficientes em rosa (f_exposicao, p_vista_traseira…) são chutes de mercado, não calibrados. Ficam parametrizados em core.model_params e um único estudo de campo estreita a faixa indicativa de ±35%.
O score 0–100

O que é realmente vendável: o ranking

Cada uma das 5 dimensões é normalizada (min-max) entre as 304 linhas, virando um sub-score 0–1. O score final é a média ponderada. Os pesos são parametrizáveis — e por campanha o perfil pode favorecer A/B ou inverter para D/E. Experimente:

Alcance · impressões35%
Densidade · pop/km15%
Perfil · classe AB20%
Exposição arterial · via20%
POIs · estabelecimentos10%
Σ pesos = 100% · normalizado automaticamente
Sub-scores de exemplo (linha 4107): alcance 0,62 · densidade 0,48 · perfil 0,71 · arterial 0,31 · POI 0,55

O diferencial

Honestidade de medição

A regra do produto: nenhum número é apresentado como mais preciso do que sua fonte permite. Isso separa o que pode ser vendido como métrica do que é só ilustração — e é o que torna o produto confiável.

✅ Vendável hoje

  • O ranking / score 0–100 entre linhas — baseado em dados medidos (população, renda, POIs, exposição arterial)
  • A comparação relativa "linha X > linha Y para o público Z"
  • Fatos operacionais verificados (tempo real): veiculação, km rodado, itinerário, pontos servidos
  • Renda por setor — é dado medido do IBGE, não proxy

⚠️ Não vendável como número exato

  • O valor absoluto de impressões — depende de coeficientes de mercado não calibrados
  • Reportado como estimativa com faixa indicativa (±~35%), ilustrativa
  • Alcance de pessoas únicas — só após passar pela matriz O-D
  • A margem ±35% é faixa indicativa, não margem estatística
🧪
O caminho para vender o absoluto: um estudo de campo calibra os coeficientes (f_exposicao, p_vista_traseira…) e estreita a faixa. Até lá, o produto vende ranking — e é transparente sobre por quê. O tempo real é o chão sólido: o que o carro de fato rodou é verificado, não estimado.

Arquitetura

Plano de dados + plano comercial

O produto separa o plano de dados (referência OOH, sem cliente) do plano comercial (campanhas, com tenant). Tudo em microsserviços hexagonais, Kafka como backbone, deploy só por GitHub Actions.

ServiçoPlanoPapelStack
uai-ooh-pipelinedadosUm repo, dois módulos: ingestor (GTFS/censo/OSM/PBH → raw, agendado) + normalizer (raw → core PostGIS + tabelas planas)Python · PostGIS
uai-ooh-realtime-pollerdadosPolling GTFS-RT (~15-20s) → Kafka + landingPython

⚡

Tempo real = o chão sólido

O poller landa a frota inteira para auditoria, mas só os carros ativos de uma campanha viram viagem consolidada. A linha vem sempre do RT (carros trocam de linha) e divergências viram alerta de execução. Resultado: km, pontos servidos e velocidade verificados, não estimados.

🗄️

PostGIS no pipeline, SELECT no serving

Todo cruzamento espacial pesado é precomputado pelo normalizer e materializado em tabelas planas. O app de produção não tem PostGIS — lê com SELECT indexado e Redis. É o mesmo padrão já usado no line_neighborhood.

Roadmap

Três fases, do dado à recorrência

F1 · PLANEJAMENTO

Inteligência estática

  • Épico 0: renda do censo ✅ · radar → v2
  • Épico 1: identidades (linha, ponto, itinerário)
  • Épico 2: contexto (censo+renda, POIs, arterial)
  • Épico 3: métricas, impressões, score 0–100
  • Épico 4: serving → app Java + endpoints
F2 · TEMPO REAL

Metrificação verificada

  • Poller GTFS-RT + Kafka
  • Consolidador de viagens (carros ativos)
  • km / velocidade / pontos por viagem
  • Mapa ao vivo + alcance verificado vs estimado
F3 · COMERCIAL

Campanha & assinatura

  • uai-cms multi-vertical (campaign.type)
  • Carros vendidos · ativação · relatório de entrega
  • Frontend separado via BFF
  • Assinatura recorrente ancorada no tempo real
